## 4. 分级缺陷清单

### P0 阻塞（不能玩 / 核心循环断 / 崩溃）

**无。** 游戏可加载运行，核心循环完整，无崩溃，file:// 双击即玩。所有 41 条断言通过（含核心循环跑通、同 seed 复现）。

### P1 应修（反馈错误 / 数值失衡 / 归因不清）

**P1-1　技术债放大系数「展示值」未钳制 → 归因误导【已修复】**
- 位置：`game/js/logic.js` `runExecution`（展示用 `ampl` 字段）与 `applyStrategy`（计算层）
- 现象（修复前）：计算层已钳制 [0.6,1.5]，但展示值未钳制，全关 L 展示 1→2.05、高初始债达 8.05，误导归因。
- 修复（团长合并修正）：抽出 `clampAmpl(debt)`，计算与展示同源；回归断言已改为"展示值恒 ≤1.5"。
- 复现（修复后验证）：`node tests/run-tests.js` → TC-07 全部 PASS。

### P2 建议（体验优化 / 文档自洽）

**P2-1**　design.md §4 映射 #6（提示词过简→工期↑）与 §7 数值表/ gameplay.md（省提示词=更快）矛盾；代码按 §7 实施。建议统一 design.md（保留"省=更快"主流意图，修订 §4 #6 文案）。
**P2-2**　design.md §4 映射 #5（过度设计→技术债↑）与 §5.1 trait 表（过度设计癖 techDebt-1，短期减债）矛盾；代码按 §5.1。建议统一（若要体现反噬则把 `overdesign.techDebt` 改为 +，并相应调整 timeline）。
**P2-3**　`generateProject`（logic.js 约 50–58 行）注释称"口碑对报酬有轻量加成（跨局累积 rep）"，但代码未使用 `player.rep`，仅 `0.8+rng*0.4` 波动。建议实现该加成或删除注释。
**P2-4**　映射 #10 的"接过多项目压榨"跨局维度未建模：每局 `energy` 重置为 10，无法体现连续接单的累积疲劳。建议跨局累积轻度疲劳或加"连续接单"成本。
**P2-5**　全开（纯重质量）恒因工期超限失败：单任务 timeline 基线 2 + 各开维度 = 4.5 周，容忍 3.5 周/任务（比值 1.286>1），任何规模都超 deadline。建议下调 `BASE_TASK_WEEKS` 或放宽 `deadlineWeeks`，给"做好"留一条成功窄路。
**P2-6**　全关（纯重速度）恒因缺陷超限失败。可接受（教因果），但建议给速度流一条窄成功路径（如靠高口碑接小项目）避免"必败"感过死。
**P2-7**　归因面板每任务都含基线工期(+2)，玩家难区分"决策贡献"与"任务固有成本"。建议把基线单独列为"任务固定成本"，增量单独高亮，提升归因可读性。
**P2-8**　`main.js` 默认策略为全关（最差预设），新玩家首局即惨败。建议默认给一个"平衡"预设降低首局挫败。
**P2-9**　`computeQualityRatio` 分母恒 +4，使极端质量比难趋近 0/1，区分度弱。建议按规模归一化。
**P2-10**　结局每局都展示、无终局态，连续同风格会反复看同一文案。建议仅在累计阈值/主动结束时展示，或随历史微调文案。
**P2-11**　`hiddenNeed` 仅以 `qualityRatio>=0.5` 给口碑±1 粗略代理"锁需求"（映射 #3 对应弱）。建议引入独立"需求锁定"决策维度或按隐藏需求类型差异化。

## 5. 玩法验证

### 5.1 核心循环是否让玩家理解决策后果（归因是否清晰可读）
- ✅ **可归因**：结算/执行日志逐任务列出「所选策略 + 触发 trait/事件 + 数值增量」，并用颜色标注正负；同 seed 可完全复现（TC-05）。
- ⚠️ **可读性扣分项**：① P1-1 放大系数展示值虚高，玩家会误判"技术债把我的数放大了 8 倍"；② P2-7 基线工期混在增量里，削弱"哪个决策导致什么"的直观感。

### 5.2 随机性是否破坏可理解性
- ✅ 随机来自 `makeRng(seed)` 且全部记录；条件型事件（newlang/rival）的结果取决于**玩家前期决策**（写没写测试、债高不高），"运气"被决策部分消化，符合 gameplay.md 设计意图（TC-06 验证）。
- ✅ 事件触发率≈0.45（实测 0.449），频率合理，不会淹没策略信号。

### 5.3 数值平衡初评（回答设计方提问）
| 设计方提问 | 实测结论 |
|---|---|
| 重质量策略是否过强？ | **否，反而偏弱**：全开（纯重质量）恒因工期超限失败（S：11.48>11）。没有"无脑全开取胜"的路径。 |
| 重速度是否必败？ | **是，纯重速度必败**：全关 S 缺陷 24.15 远超容忍 3。但"重速度"若夹带部分评审/测试（混合）仍可成（平衡例=优）。即纯极端必败，中庸可赢。 |
| 全开是否过劳失败？ | **会失败，但主因是工期而非过劳**：全开 L 精力-22 触发疲劳(+11缺陷)，但结算先因 timeline 超 deadline 判失败。疲劳惩罚存在且正确，只是非首要失败因。 |

> 平衡小结：当前设计形成"极端双输、中庸单赢"的格局——这契合游戏"在快与稳之间掂量"的核心张力（gameplay.md 明确"全选快不是爽点"）。唯一要修的是让"做好"也有可行成功路径（P2-5），以及修正展示误导（P1-1）。
